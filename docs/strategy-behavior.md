# 三种 Maker 策略产品说明

本文用产品和运营能直接理解的方式，说明当前系统中三种策略的真实行为：

- `BID_ASK_MAKER · 买一至买五/卖一挂单`
- `BUY_PRICE_MAKER · 买入价退出`
- `FEE_AWARE_MAKER · 手续费保护 Maker`

本文回答五个核心问题：什么时候买、买什么价格、买到后怎么卖、订单长时间不成交怎么办、停止或重启后怎么办。

> 本文描述当前代码行为，不代表收益承诺，也不构成交易建议。
>
> 最后按代码核对：2026-09-09。行为基准为 `HighFrequencyVolumeChurnEngine`、
> `AccountTradingRuntime`、`AccountRiskCoordinator`、`MarketSignalEvaluator`、`AccountUserDataStream`
> 和 `application.yml` 的当前实现；如果环境变量或控制台为账户/交易对保存了覆盖配置，以覆盖值为准。

---

## 1. 先看结论

三种策略都使用 `LIMIT_MAKER` 买单。`BID_ASK_MAKER` 可以选择买一至买五，另外两种策略固定买一；其他主要差别是“是否限制追高”和“刚买入后的第一张卖单如何定价”。

| 策略 | 买入价 | 初始卖价 | 初始卖单 | 买入锚点 | 超时目标价 |
|---|---|---|---|---|---|
| `BID_ASK_MAKER` | 配置的买一～买五，默认买一 | `max(卖一, 买入均价 + 配置 tick 数)` | 普通 `LIMIT` | 无 | 最新卖一 |
| `BUY_PRICE_MAKER` | 买一 | 实际买入均价（按 tick 向上取整） | 普通 `LIMIT` | 无 | 最新卖一 |
| `FEE_AWARE_MAKER` | 买一 | `max(卖一, 手续费保护价)` | `LIMIT_MAKER` | 有 | 最新卖一 |

三种策略的买单都是 `LIMIT_MAKER`。卖单超时后都不再坚持初始价格底线。

控制台新建策略配置时默认选择 `FEE_AWARE_MAKER`；生产账户应为当前交易对保存明确的策略配置。旧版 `CURRENT` 模式已经删除。

一句话理解：

- `BID_ASK_MAKER`：可选买一至买五买入，卖一卖，初始卖价至少比买入价高配置的 tick 数；买入档位和卖出加价均默认 `1`。
- `BUY_PRICE_MAKER`：买一买，第一张卖单直接挂实际买入均价；超时后改挂最新卖一。
- `FEE_AWARE_MAKER`：买一买，但不允许无限追高；刚买到时先挂手续费保护卖价。
- 三种策略的卖单一旦超过检查时间，都会把“尽快释放仓位”放在第一位，不再坚持原来的价格底线。

## 2. 产品需要知道的盘口名词

### 买一

当前市场里最高的买入报价。

例如：

```text
买一 1.0000
```

表示当前有人愿意以 `1.0000` 买。

### 卖一

当前市场里最低的卖出报价。

例如：

```text
卖一 1.0002
```

表示当前有人愿意以 `1.0002` 卖。

### tick

交易所允许的最小价格变化单位。

如果 tick 是 `0.0001`，合法价格可以是 `1.0000`、`1.0001`、`1.0002`，不能是 `1.00015`。

系统所有买卖价格最终都会按 tick 取整：

- 买单通常向下取整，避免超过计划买价。
- 需要保护底线的卖单向上取整，避免低于保护价。

### `LIMIT_MAKER` 和普通 `LIMIT`

- `LIMIT_MAKER`：只允许挂在订单簿里，不允许一提交就立即吃掉对手盘；如果会立即成交，交易所可能拒绝该订单。
- 普通 `LIMIT`：指定一个限价，可以挂在订单簿里，也可能因为市场变化立即成交。

## 3. 三种策略共同的完整流程

```text
人工启动账户
  ↓
确认账户、行情、订单、持仓和风控安全
  ↓
空仓时按策略买入档位挂 LIMIT_MAKER 买单
  ↓
买入全部成交，或部分成交已达到可卖条件
  ↓
撤掉剩余买单，按所选策略挂第一张卖单
  ↓
卖单成交并确认空仓
  ↓
等待“卖后买入等待秒数”
  ↓
进入下一轮
```

三种策略都不会同时无序地挂多轮买卖单。系统会先完成或处理当前订单，再进入下一阶段。

### 一个账户同时运行多个币种

账户配置增加 `symbols` 清单后，同一个 API 账户最多可以同时运行 5 个 USDT 交易对。例如：

```json
{
  "account-a": {
    "alias": "bot-a",
    "apiKey": "...",
    "secretKey": "...",
    "symbols": ["PROMUSDT", "SAHARAUSDT"],
    "symbolStrategies": {
      "PROMUSDT": {"mode": "BID_ASK_MAKER"},
      "SAHARAUSDT": {"mode": "FEE_AWARE_MAKER"}
    }
  }
}
```

产品上会看到两个“账号 / 币种运行实例”：`bot-a · PROMUSDT` 和 `bot-a · SAHARAUSDT`。两者可以分别启动、停止和修改策略，但不是两个互不相关的账户：

- 共用一条账户 User Data WebSocket，订单和成交事件按交易对分发，不会串单；
- 每个币种有自己的行情 WebSocket、状态机、活动订单、持仓成本、卖单超时计时、每日成交量和策略配置；
- 买单请求按账户串行提交，避免两个币种同一时刻争抢 USDT；
- 启动任一币种前，系统用同一份账户余额快照核对全部配置币种；只要其中一个币种的远程余额与当日本地持仓账本不一致，整个账户暂不允许开新仓；
- 可用 USDT 和尚未终结的买单金额按账户统一预留；余额不足被交易所拒绝时等待 30 秒再试，避免每秒重复请求；
- 最大库存金额按账户全部币种的持仓和活动买单合计计算；
- 最大日内回撤既保留单币种保护，也增加账户全部币种合计保护；
- BNB 余额检查按账户共享，30 秒缓存期内不会因币种增加而重复查询；
- 一个币种达到自己的 `510 USDT` 日成交量上限，只停止该币种，不会停止另一个币种；BNB 低于 `1 USDT` 属于账户级问题，所有运行币种都会停止新买入并分别安全退出。

如果账户流断线且重连失败，同账户所有运行币种都会保护停机；某一个币种自己的行情流失败，只影响该币种。收到未配置交易对的真实成交事件时，系统会保守停止这个账户下所有运行币种，要求人工核对。

没有配置 `symbols` 的旧账户继续按单币种方式运行，配置和接口保持兼容。产品可在“账户交易对配置”中增加或删除交易对：页面仅把非敏感清单写入 SQLite `runtime_setting`，不会修改服务器 env；后续启动时 SQLite 清单优先于 env 的初始 `symbols`。修改前要停止该账户全部币种并确保没有活动订单；保存后系统会优先热应用到当前账户运行时，动态新增/移除币种 engine，并继续复用同一条账户 User Data WebSocket。若热应用失败，SQLite 配置仍保留，重启服务后按已保存清单生效。

多币种账户需要在产品中选择具体币种后单独启动。旧版账户级“启动”接口会拒绝多币种账户，防止误以为所有币种都已启动；账户级“停止”接口则会依次停止该账户下的全部币种，作为安全兜底。

### 默认时间

| 配置 | 未单独配置时的默认值 | 含义 |
|---|---:|---|
| 买单超时 | 20 秒 | 买单挂够这个时间后，检查它是否仍在策略配置的买入档位 |
| 卖单检查 | 120 秒 | 卖单挂够这个时间后，检查它是否仍在卖一 |
| 卖后买入等待 | 60 秒 | 卖完并确认空仓后，等待多久才开始下一轮 |

每个账户、每个交易对都可以单独配置这些时间。

时间配置范围：买单超时为 `1 秒～30 分钟`；卖单检查为 `1 秒～24 小时`；卖后买入等待为 `0 秒～24 小时`。填 `0` 只允许用于卖后等待，表示卖完确认空仓后不额外等待。

### 当前全局安全默认值

下面是仓库 `application.yml` 的当前默认值；生产环境仍可能通过受保护配置覆盖：

| 项目 | 当前默认值 | 实际作用 |
|---|---:|---|
| 单笔金额 | 12 USDT | 每次计划买入的名义金额 |
| LIVE 单笔上限 | 30 USDT | 控制台不能把单笔金额调得更高；已有账户金额不会自动放大 |
| 每日成交量上限 | 510 USDT | 每账户、每交易对、UTC 每日分别计算 |
| 最大库存名义额 | 40 USDT | 单币种先检查自身，再按同账户全部币种持仓和活动买单合计检查；不主动市价卖出 |
| 最大日内回撤 | 8 USDT | 单币种和同账户全部币种合计任一触发后阻止新买入；生产可由 `BINANCE_STRATEGY_MAX_DAILY_DRAWDOWN_USDT` 覆盖 |
| 库存持有超时 | 10 分钟 | 触发后阻止继续买入；已有卖出流程继续管理仓位 |
| BNB 最低价值 | 1 USDT | 低于后停止新买入，空仓后停止账户 |
| 行情连接存活检查 | 45 秒 | 连续没有任何入站帧才按断流处理 |

### 策略配置什么时候生效

- 当前处于 `IDLE` 且没有活动订单：保存成功后直接应用。
- 当前处于 `BUYING` 或 `SELLING`：新配置先排队，当前订单和仓位流程完成、回到 `IDLE` 后才应用。
- 配置按“账户 + 交易对”写入 SQLite，重启后优先于环境变量中的同交易对配置恢复。
- 修改策略不会中途改变正在执行的订单，也不会用新策略重新解释旧订单。
- 控制台保存后会常驻显示“保存成功”“等待当前订单完成后应用”或“保存失败”，不再只依赖瞬时提示框。锚定价格点击“删除手动值，恢复自动”并应用后，会清除 SQLite 中的手动值；输入框随后显示系统推荐值属于自动模式，不代表手动值没有删除。

控制台已经没有“运行模式”和“LIVE 解锁”按钮。系统只支持真实交易；是否允许启动由服务器端 `BINANCE_LIVE_TRADING_ENABLED=true` 控制，默认关闭。这个开关不是账户页面上的临时解锁状态。

## 4. 共同的买入规则

### 4.1 买入价格

`BUY_PRICE_MAKER` 和 `FEE_AWARE_MAKER` 的基础买价是：

```text
买入价 = 当前买一价
```

然后按 tick 向下取整，并使用 `LIMIT_MAKER` 挂单。

`BID_ASK_MAKER` 则读取现有五档行情，按配置选择：

```text
1 = 买一
2 = 买二
3 = 买三
4 = 买四
5 = 买五
```

默认值是 `1`，因此旧配置行为不变。选择买二至买五时，如果对应档位暂时不存在或五档行情已经过期，系统先等待深度行情，不会自动回退到更高的买一价，也不会额外调用 REST 接口。

例子：

```text
当前买一：1.00034
tick：0.0001
最终买价：1.0003
```

### 4.2 哪些行情指标不再阻止买入

当前三种策略都不再因为下面这些技术指标暂停买入：

- 主动卖盘过强；
- 短线下跌；
- 下跌后尚未收复；
- 买一力量不足；
- 顶层盘口较薄；
- 五档深度较薄；
- 短线波动较大。

这些指标即使仍出现在诊断数据中，也只用于观察，不决定是否挂买单。

### 4.3 真正会阻止买入的情况

下面这些属于安全底线，仍然会阻止买入：

- 账户没有人工启动；
- 服务器没有开启真实交易开关 `BINANCE_LIVE_TRADING_ENABLED=true`；
- 账户成交流或必要行情不可用；
- 当前交易对存在无法安全接管的活动订单；
- 当前存在成本未知或数量对不上的可交易持仓；
- API 请求权重达到安全线；
- 下单数量或金额不满足交易所最小规则；
- 风控触发，例如最大持仓、日内回撤或库存持有超时；
- 今日成交量达到该账户配置的上限；
- 账户 BNB 价值低于 `1 USDT`；
- 使用 `FEE_AWARE_MAKER` 时，当前买一超过锚点允许价。

因此，“账户显示运行中”不等于“一定马上产生买单”。运行中只表示状态机正在工作，真正下单还需要通过这些安全检查。

### 4.4 买单挂久了怎么办

买单达到“买单超时”后：

- 当前订单仍在策略配置的买入档位：保留原单，继续排队并重新计时。
- 当前订单已经不在该档位：撤掉旧单，等待按新的对应档位重新挂。
- 配置买二至买五但暂时拿不到该档位：保留现有买单，本轮检查重新计时，不盲目撤单。
- 不会改成市价单追买。

`FEE_AWARE_MAKER` 还有一个锚点例外：检查超时时，如果最新买一已经超过允许上限，但原买单价格仍在允许上限以内，系统会保留这张更低的 Maker 买单，不会为了追到最新买一而撤换；只有原买单本身也超过允许上限时才撤单。

例子：

```text
配置：买三
原买单：0.9998
20 秒后买三仍是 0.9998
结果：保留原单
```

```text
配置：买三
原买单：0.9998
20 秒后买三变成 0.9997
结果：撤掉原单，下一次按最新买三重新挂
```

### 4.5 买单只成交了一部分

如果已买到的部分已经达到交易所最小可卖条件，系统会：

1. 撤掉尚未成交的买单；
2. 对账实际成交数量和手续费；
3. 立即进入卖出阶段。

如果已成交部分太小，暂时无法形成有效卖单，系统会把它标为小额库存，等待后续处理，不会提交交易所一定会拒绝的卖单。

## 5. `BID_ASK_MAKER` 产品行为

### 5.1 适用目标

这个策略更强调贴近盘口、提高成交机会。

它没有买入锚点，也不保证扣除全部手续费后保本。它只在第一张卖单上保留一个简单底线：卖价必须比买入均价高配置的 tick 数。

“买入档位”可配置 `1～5`，分别代表买一至买五，默认 `1`。档位越深，买入价格通常越低，但排队和等待成交的时间也可能更长。买单超时后仍按同一配置档位检查、保留或撤换。

### 5.2 第一张卖单怎么算

```text
加价金额 = 当前交易对 tick × 初始卖价加价 ticks

初始卖价 = max(当前卖一, 买入均价 + 加价金额)
```

第一张卖单使用普通 `LIMIT`。

“初始卖价加价 ticks”默认是 `1`，可在控制台的策略配置区域修改，范围为 `1～10,000`。控制台会根据当前交易对展示 `1 tick` 具体增加多少 USDT。

例如当前交易对 `1 tick = 0.0001 USDT`：

- 配置 `1 tick`，买入均价上方增加 `0.0001 USDT`；
- 配置 `3 tick`，买入均价上方增加 `0.0003 USDT`；
- 配置 `10 tick`，买入均价上方增加 `0.0010 USDT`。

#### 例子 A：卖一高于买价

```text
买入均价：1.0000
当前卖一：1.0020
tick：0.0001
初始卖价：1.0020
```

#### 例子 B：卖一低于买价

```text
买入均价：1.0000
当前卖一：0.9998
配置：1 tick
买入价上方 1 tick：1.0001
初始卖价：1.0001
```

此时不会一开始就按 `0.9998` 亏价卖出。

### 5.3 卖单超时怎么办

卖单达到“卖单检查”时间后，系统只比较两件事：原订单价格和最新卖一。

```text
如果原订单价 == 最新卖一：
    不撤单，保留排队位置，重新开始下一轮计时

如果原订单价 != 最新卖一：
    撤掉旧单
    对账旧单是否有部分成交
    按最新卖一重新挂普通 LIMIT 卖单
```

超时后的目标价只有一个：

```text
新卖价 = 最新卖一
```

超时后不再使用“买入价上方配置 tick 数”的底线。

#### 例子 C：原单仍在卖一

```text
原卖单：1.0020
120 秒后最新卖一：1.0020
结果：不撤单，重新计时 120 秒
```

#### 例子 D：卖一下移

```text
买入均价：1.0000
原卖单：1.0020
120 秒后最新卖一：0.9990
结果：撤掉 1.0020，按 0.9990 重新挂卖单
```

这里可能产生亏损。原因是卖单已经长时间没有成交，超时阶段的产品目标已经从“守住买价”切换为“尽快卖出并释放资金”。

#### 例子 E：暂时拿不到卖一

系统不会盲目撤单，而是保留原卖单，等下一个“卖单检查”周期再判断。

## 6. `BUY_PRICE_MAKER` 产品行为

### 6.1 适用目标

这个策略希望第一张卖单尽量容易成交，同时不主动在刚买入后就降价。

它没有买入锚点，也不计算手续费保护价。与 `BID_ASK_MAKER` 的主要区别是：第一张卖单不看当前卖一，直接按本轮实际买入均价挂出。

### 6.2 第一张卖单怎么算

```text
初始卖价 = 本轮实际买入成交额 ÷ 本轮实际买入数量
```

最终价格按交易所 tick 向上取整，第一张卖单使用普通 `LIMIT`。

#### 例子 A：买入价正好符合 tick

```text
实际买入均价：1.0000
tick：0.0001
当前卖一：1.0020
初始卖价：1.0000
```

即使当前卖一是 `1.0020`，第一张卖单仍按买入均价 `1.0000` 提交。普通 `LIMIT` 在盘口允许时可能立即成交。

#### 例子 B：多笔成交后的均价不符合 tick

```text
实际买入均价：1.00005
tick：0.0001
初始卖价：1.0001
```

这里向上取整是为了生成交易所接受的合法价格，不是额外增加利润目标。

### 6.3 卖单超时怎么办

达到“卖单检查”时间后，处理规则与 `BID_ASK_MAKER` 相同：

```text
如果原订单价 == 最新卖一：
    不撤单，保留排队位置，重新开始下一轮计时

如果原订单价 != 最新卖一：
    撤掉旧单
    对账旧单是否有部分成交
    按最新卖一重新挂普通 LIMIT 卖单
```

超时后不再保留买入均价底线。

#### 例子 C：买入价卖单没有成交

```text
买入均价及原卖单：1.0000
120 秒后最新卖一：0.9992
结果：撤掉 1.0000，按 0.9992 重新挂普通 LIMIT
```

这次退出可能产生价差亏损和手续费成本。该机制的目标是避免仓位长期占用，而不是保证保本。

### 6.4 卖完后什么时候再买

卖单全部成交并确认交易所已经空仓后，等待“卖后买入等待秒数”，然后重新按当前策略的买入档位挂下一笔 `LIMIT_MAKER` 买单。默认等待 `60` 秒，可按账户和交易对配置。

## 7. `FEE_AWARE_MAKER` 产品行为

### 7.1 适用目标

这个策略增加两层保护：

1. 买入时限制价格不断上移，减少“越买越高”；
2. 买入后的第一张卖单先尝试覆盖持仓成本和预计卖出手续费。

它不额外追求利润。手续费保护价就是初始卖出的主要目标。

### 7.2 买入锚点是什么

系统同时使用两个锚点：

- 上一轮最高买入价：控制下一轮相对上一轮最多追高多少。
- 初始锚点：控制本次策略运行期间累计最多追高多少。

初始锚点的来源顺序：

1. 产品或运营手动填写的锚定价格；
2. 没有手动填写时，取最近 5 笔 `FEE_AWARE_MAKER` 买入价的平均值；
3. 没有可用近期买价时，使用运行状态能够安全恢复出的上一轮买入上限。

控制台会展示系统推荐锚点。未修改时继续使用系统自动值；手动填写后会同时展示“手动值 / 推荐值”。

第一次运行且没有手动锚点、没有历史买价、也没有可恢复运行状态时，系统暂时没有锚点，因此第一轮买入不会被锚点限制。第一轮买入完成后，系统记录本轮最高真实买入价，作为下一轮的“上一轮锚点”；最近买入价最多保留 5 个，并随必要运行状态一起持久化。

手动填写锚定价格后，该价格会同时成为初始累计锚点和当前买入基准，并按 tick 向上取整。

### 7.3 允许最高买价怎么算

```text
单轮上限 = 上一轮最高买入价 × (1 + 单轮最大追高 bps)

累计上限 = 初始锚点 × (1 + 累计最大追高 bps)

最终允许最高买价 = min(单轮上限, 累计上限)
```

`bps` 是万分之一：

- `10 bps = 0.10%`
- `50 bps = 0.50%`
- `100 bps = 1.00%`
- `1000 bps = 10.00%`

单轮最大追高可配置 `0～100 bps`（最多 1%）；累计最大追高可配置 `0～1000 bps`（最多 10%）。累计值只放宽长期总上限，最终买价仍同时受单轮上限约束。

当当前买一不高于原买入锚点时，可以直接进入正常买入检查。

当当前买一高于原买入锚点时，先等待“买入锚点等待秒数”；等待结束后，也只有不超过最终允许最高买价时才能买。

默认配置：

- 买入锚点等待：`1800` 秒；
- 单轮最大追高：`0 bps`；
- 累计最大追高：未配置时跟随单轮值。

默认 `0 bps` 的含义是：即使等待结束，也不允许买得比锚点更高，只能等价格回落。

#### 例子 A：完全不追高

```text
上一轮最高买价：1.0000
初始锚点：1.0000
单轮最大追高：0 bps
累计最大追高：0 bps
当前买一：1.0001
```

结果：当前买一高于允许价 `1.0000`，不挂买单。

#### 例子 B：允许小幅追高

```text
上一轮最高买价：1.0000
初始锚点：1.0000
单轮最大追高：10 bps
累计最大追高：20 bps
```

计算：

```text
单轮上限：1.0010
累计上限：1.0020
最终允许最高买价：1.0010
```

- 当前买一 `1.0008`：等待时间满足后可以买。
- 当前买一 `1.0015`：超过最终上限，等待再久也不买。

#### 例子 C：累计上限更严格

```text
上一轮最高买价：1.0200
初始锚点：1.0000
单轮最大追高：50 bps
累计最大追高：100 bps
```

计算：

```text
单轮上限：1.0251
累计上限：1.0100
最终允许最高买价：1.0100
```

即使上一轮已经买到 `1.0200`，系统也不会继续以它为基础不断向上追价；累计锚点会把最高买价限制在 `1.0100`。

### 7.4 第一张卖单怎么算

```text
持仓成本单价 = 当前持仓成本 ÷ 当前持仓数量

手续费保护价 = 持仓成本单价 ÷ (1 - 预计卖出费率)

初始卖价 = max(当前卖一, 手续费保护价)
```

最终价格按 tick 向上取整，第一张卖单使用 `LIMIT_MAKER`。

手续费率来源顺序：

1. 当前策略手动填写的 Maker 费率；
2. 交易所返回的当前账户、当前交易对真实费率；
3. 无法读取时使用系统保守默认值。

交易所费率读取成功后缓存 15 分钟。计算时使用标准 Maker/Seller 费率，加上特殊费率和税费；不会预先扣除 BNB 折扣，因为实际成交时 BNB 可能不足。读取失败时当前默认按 `10 bps` 估算。

兼容字段 `targetNetProfitBps`、全局 `takeProfitBps` 以及旧版 15 秒阶梯改价参数，当前三种策略均不参与实际价格计算。`FEE_AWARE_MAKER` 初始卖价只保护已记录持仓成本和预计卖出手续费，不额外叠加目标利润。

#### 例子 D：卖一已经足够高

```text
持仓成本单价：1.0000
预计卖出费率：10 bps
手续费保护价：约 1.0011
当前卖一：1.0030
初始卖价：1.0030
```

#### 例子 E：卖一低于手续费保护价

```text
持仓成本单价：1.0000
预计卖出费率：10 bps
手续费保护价：约 1.0011
当前卖一：1.0005
初始卖价：约 1.0011，再按 tick 向上取整
```

系统不会在第一张卖单上直接降到 `1.0005`。

### 7.5 卖单超时怎么办

超时处理与 `BID_ASK_MAKER` 的判断原则相同：

```text
如果原订单价 == 最新卖一：
    保留原 LIMIT_MAKER 卖单，重新开始下一轮计时

如果原订单价 != 最新卖一：
    撤掉旧单
    对账已成交数量和剩余库存
    按最新卖一重新挂 LIMIT_MAKER 卖单
```

超时后的目标价为：

```text
新卖价 = 最新卖一
```

此时不再强制使用手续费保护价。

#### 例子 F：手续费保护价长期无法成交

```text
持仓成本单价：1.0000
手续费保护价：1.0011
原卖单：1.0011
120 秒后最新卖一：0.9995
```

结果：撤掉原卖单，按最新卖一 `0.9995` 重新挂 `LIMIT_MAKER`。

这次卖出可能无法赚回手续费，也可能产生价差亏损。超时机制的目的就是避免为了守手续费保护价而长期占用仓位。

如果原卖单本身就是最新卖一，则不撤单，也不会因为“已经超时”而反复丢失排队位置。

## 8. 每日成交量上限

每个账户、每个交易对可以配置每日真实成交量上限，默认是 `510 USDT`，按 UTC 日期分别计算。切换交易对不会把另一个币种当天的成交量加到当前交易对。

买入和卖出都计入成交量。

例如一轮交易：

```text
买入成交额：12 USDT
卖出成交额：约 12 USDT
本轮累计成交量：约 24 USDT
```

达到或超过上限后：

- 空仓：立即停止当前币种策略。
- 正在挂买单：撤销买单并对账，然后停止。
- 已持仓或正在卖出：停止新买入，但保留退出流程；卖完并确认空仓后自动停止。

因为已有仓位必须先卖完，所以最终成交量可能略高于配置上限。

UTC 日期进入新的一天后，成交量重新计算；但前一天已自动停止的账户不会自行启动，仍需人工启动。

## 9. BNB 余额保护

账户的第一个币种策略启动时会强制检查一次 BNB；同账户其他币种复用该结果。策略运行期间，整个账户最多每 30 秒检查一次 BNB 总余额，并按 `BNBUSDT` 最新价换算成 USDT。已经停止的币种不会因为控制台刷新而持续请求 BNB 余额。

当 BNB 价值低于 `1 USDT`：

- 空仓：立即停止当前币种策略。
- 正在挂买单：撤销买单并对账。
- 已持仓或正在卖出：不直接撤掉退出卖单，先完成卖出，确认空仓后停止。

这个规则只影响 BNB 不足的账户，不影响其他账户。

如果 BNB 余额或价格暂时读取失败，系统沿用最近一次有效结果，并至少等待 30 秒再请求；从未取得有效结果时，不会把“未知”误判成低于 `1 USDT`，也不会在行情每次跳动时反复请求交易所。

## 10. 停止、重启和持仓恢复

### 10.1 人工点击“停止当前”

人工停止会尝试撤销当前活动订单并核对订单和余额。

- 空仓且没有活动订单：安全停止，状态回到 `IDLE`。
- 仍有可交易持仓：不能假装已经安全空仓，控制台会明确提示仍有持仓或进入保护状态。
- 只有不足交易所最小卖出条件的小额余额：作为粉尘保留。

人工停止与“达到成交量/BNB 限制后的自动停止”不同：自动停止会优先让已经存在的 SELL 完成，再停止账户。

### 10.2 服务重启

服务重启后，账户默认不会自动开始新一轮交易，必须人工启动。

系统不会把本地保存的持仓数量当作交易所真实余额。启动时的活动订单、可用/冻结余额和可交易持仓必须从交易所重新确认。

本地 SQLite 会保存三类辅助信息：

- 今日成交量、手续费、盈亏和成本的聚合账本；
- 每笔真实成交的价格、数量、成交额、手续费和成交 ID；
- 必要的本进程订单身份、价格、挂单时间和 `FEE_AWARE_MAKER` 锚点恢复状态。

这些数据用于记账、防重复处理和安全恢复，但不能绕过交易所余额与活动订单核验。

### 10.3 重启后交易所仍有本进程卖单

人工再次启动时，系统可以恢复一张由本进程创建的 SELL 单，但必须同时满足：

- 当前交易对只有这一张活动订单；
- 订单 ID、客户端订单 ID、方向与本地运行状态完全一致；
- 订单还没有出现无法对账的部分成交；
- 系统能够从交易所成交历史恢复正数持仓数量和成本；
- 交易所当前持仓与恢复出的持仓在一个 stepSize 以内一致。

满足时，系统恢复为 `SELLING`，沿用原挂单价格和原挂单时间继续管理；卖单检查计时不会无条件从零开始。不满足时不会猜测接管，而是提示人工对账。

### 10.4 有持仓但没有活动订单

人工重新启动时，系统先以交易所余额为准。如果交易所存在可卖持仓，而当前内存无法确认成本，系统会按每段 24 小时向前分页读取成交历史，最多回看 30 天，找到最近一次从空仓开始形成当前持仓的完整成交链，并恢复：

- 未平仓数量；
- 该笔未平仓的加权买入成本；
- 开仓时间；
- 与交易所当前余额是否一致。

能够恢复且数量一致时，系统进入 `SELLING`，按当前策略重新挂卖单。

历史成交恢复只在人工启动时执行一次，不用于控制台轮询。跨日前的成交仅用于恢复当前未平仓成本，不会加入今天的成交量、手续费、已实现盈亏或闭环次数；这些统计仍严格按当前 UTC 日期计算。本地 SQLite 中的持仓聚合也不会替代交易所余额成为持仓来源。

例如：

```text
昨天策略买入后仍持仓
→ 人工停止，卖单被撤销
→ 第二天再次启动当前账号的这个币种策略
→ 系统从交易所历史成交恢复这笔未平仓成本
→ 重新进入卖出阶段
→ 昨天的买入成交不计入今天交易量和手续费
```

### 10.5 为什么有时会要求人工对账

出现下面任一种情况时，系统不会猜测订单和成本：

- 交易所有活动订单，但不能确认是当前进程管理的订单；
- 有持仓，但最多 30 天的交易所成交仍无法还原成本；
- 远程成交还原的数量与交易所余额不一致；
- 收到不属于当前进程订单的成交回报；
- 撤单结果或成交明细无法确认。

典型提示：

```text
发现未由本进程恢复的活动订单，需先人工对账
```

```text
发现既有可交易标的持仓，但交易所历史成交无法还原成本或与余额不一致；拒绝自动接管
```

这时产品或运营需要在交易所确认：活动订单、当前余额、最近成交、订单是否部分成交，然后再决定保留、撤销或手工处理。

## 11. 控制台状态怎么理解

| 控制台内容 | 产品含义 |
|---|---|
| `FEE_AWARE_MAKER` | 当前使用手续费保护策略 |
| `BID_ASK_MAKER` | 当前使用可配置买一至买五、卖一退出策略 |
| `BUY_PRICE_MAKER` | 当前使用买入价退出策略 |
| `运行中`（绿色） | 状态机正在运行，不代表一定马上下单 |
| `已停止`（红色） | 当前账号的这个币种策略不会发起新交易 |
| `IDLE` | 当前没有正在管理的买卖单 |
| `BUYING` | 当前正在管理买单 |
| `SELLING` | 当前正在管理卖单或持仓退出 |
| `HALTED` | 因异常或安全原因进入保护停机，需要查看状态说明 |

策略名称和策略阶段不是同一个概念。例如：

```text
策略名称：FEE_AWARE_MAKER
策略阶段：SELLING
运行状态：运行中
```

这表示账户正在使用手续费保护策略管理一张卖单。

## 12. 产品选型建议

### 选择 `BID_ASK_MAKER`

适合更关注贴近盘口和成交机会，并且可以接受：

- 没有买入追高锚点；
- 初始卖单不做完整手续费保护；
- 卖单超时后可能低于买入价成交。

### 选择 `BUY_PRICE_MAKER`

适合希望第一张卖单直接回到买入价、减少等待价差，并且可以接受：

- 不使用买入追高锚点；
- 第一张普通 `LIMIT` 卖单可能立即成交，也可能产生手续费净亏损；
- 卖单超时后会改挂最新卖一，可能低于买入价成交。

### 选择 `FEE_AWARE_MAKER`

适合更关注控制追高和第一阶段手续费保护，并且可以接受：

- 当前价格超过锚点时可能长时间没有买单；
- 手续费保护卖价可能需要更久才能成交；
- 卖单超时后仍会切换为最新卖一，保护价不再是硬底线。

### 三种策略都不能保证的事

三种策略都不能保证不亏损，原因包括：

- 买入后市场下跌；
- 卖单超时后按较低卖一退出；
- 普通 `LIMIT` 可能按 taker 成交；
- 手续费折算和实际成交价格变化；
- 部分成交、滑点、盘口变化和交易所延迟。

`FEE_AWARE_MAKER` 只是在第一张卖单上尝试保护成本和手续费，不等于整轮交易一定保本。

## 13. “为什么没有下单”排查顺序

产品和运营按以下顺序查看即可：

1. 账户是否显示绿色“运行中”。
2. 当前阶段是否已经是 `BUYING` 或 `SELLING`。
3. 是否存在活动订单或可交易持仓。
4. 状态说明是否要求人工对账。
5. 今日成交量是否达到上限。
6. BNB 价值是否低于 `1 USDT`。
7. API 权重、账户流和行情是否正常。
8. 如果是 `BID_ASK_MAKER` 且配置买二至买五，检查相应五档深度是否存在且新鲜。
9. 如果是 `FEE_AWARE_MAKER`，检查当前买一是否超过锚点允许价。
10. 检查下单金额是否满足交易所最小成交额和数量精度。

不要再把“主动卖盘过强”“买一力量不足”“短线下跌”等旧行情指标当作当前版本不下单的原因。

## 14. 实时订单列表与 WebSocket 断线

### 14.1 所有账户当前买单 / 卖单

当前订单列表不再每 30 秒调用交易所 REST 接口。

1. 某个账户策略启动成功时，用 REST 读取一次该账户的全部活动订单，建立初始快照。
2. 之后根据 Binance 账户 WebSocket 的订单事件实时维护：
   - `NEW`：加入订单；
   - `PARTIALLY_FILLED`：更新订单的累计成交量和剩余状态；
   - `FILLED`、`CANCELED`、`EXPIRED`、`REJECTED`：从活动订单列表移除。
3. 服务端再通过控制台现有 WebSocket 把完整活动订单快照实时推送到浏览器。
4. 账户 WebSocket 重连成功后，只额外执行一次 REST 对账，补齐断线期间可能遗漏的事件。

因此，控制台一直打开不会产生固定周期的活动订单 REST 请求，也不会因为账户数量增加而每 30 秒集中消耗 API 权重。

订单展示按账户隔离：一个账户的 REST 初始快照或重连对账失败时，保留该账户上一份有效数据，其他账户继续显示；缺少账户 ID、订单 ID 等关键字段的异常记录会被忽略。控制台初次连接时，最近成交和当前订单分开发送，因此订单快照异常不会再使整个控制台 WebSocket 建连失败。

停止账户不会为了刷新这个列表而定时读取交易所活动订单。因此，如果策略从未成功启动、服务刚重启且账户保持停止，列表可能暂时没有该账户订单；这不等于交易所一定没有订单，启动安全检查仍会重新查询。

### 14.2 全部账号最近 10 条成交记录

- 只接收 Binance 账户 WebSocket 的真实 `TRADE` 事件；
- 服务端合并各账户事件，并通过控制台 WebSocket 实时推送最近 10 条；
- 不定时调用 `/api/v3/myTrades` 补全，因此不持续消耗成交历史 REST 权重；
- 记录只保存在当前进程内存中，服务重启后从新的成交事件开始显示；
- 最近成交和当前订单是两个独立消息，一个模块异常不会清空另一个模块已经显示的数据。

### 14.3 `1001` 瞬断怎么处理

`1001` 通常表示 WebSocket 连接被正常关闭或服务端轮换连接。当前处理原则是“先恢复，恢复失败才停机”：

- 行情 WebSocket 第一次收到 `1001`：账户保持运行，但没有新行情时不会继续推进下单状态机；系统立即安排重连。
- 行情重连后收到第一帧新行情：认为恢复成功，继续原来的策略状态。
- 账户 WebSocket 第一次收到 `1001`：账户保持运行，订单状态机暂不继续动作；重连订阅成功后立即做一次活动订单 REST 对账，再恢复处理。
- 重连建立失败、重连连接再次关闭、认证失败，或连接长时间没有任何数据帧：按真正断线处理，执行原有保护停机逻辑。
- 非 `1001` 的连接错误和异常关闭仍直接执行保护停机并继续尝试重连，不放宽现有安全底线。

例子：账户正在管理一张卖单时收到一次 `1001`，1 秒后重连成功。策略不会取消这张卖单，也不会停机；系统对账确认卖单仍然活动后继续管理。如果重连失败，则账户进入保护停机，避免在无法确认订单状态时继续交易。

## 15. 今日数据和汇总页面的数据来源

不同页面的数据目的不同，不能把它们理解成同一种刷新方式。

### 15.1 当前账户 / 币种状态卡片

- 运行中和停止后的页面轮询都只读取 SQLite 每日聚合及内存状态，不会因为打开控制台反复请求交易所。
- 策略启动时，REST 按页读取当天全部成交并补齐本地缓存；不再受单次最多 1000 条限制。
- 策略运行后，每个 `TRADE` WebSocket 事件立即写入成交明细并累加每日聚合，所以卡片实时变化。
- 账户 WebSocket 重连成功后，从数据库最后一个成交 ID 开始用 REST 增量补齐断线期间的数据，不重新查询全天。
- 策略停止期间发生的外部手工成交不会主动回查；下次人工启动时统一补齐。

### 15.2 今日账户交易汇总

`/today.html` 按 UTC 今日展示所有账户：

- 每个账户今天交易过的币种；
- 买入成交量、卖出成交量和总成交量；
- 已折算为 USDT 的手续费；
- 已实现净盈亏，以及亏损账户合计。

该页面每 10 秒读取 SQLite 每日聚合，不直接请求 Binance，因此不会增加交易所 API 权重。单个账户统计读取异常时只标记该账户，其他账户继续展示。它展示的是已经被本进程账户事件或受控 REST 对账写入账本的成交；账户停止期间发生的外部手工成交不会因为打开此页面而主动回查补齐。

### 15.3 近 10 天汇总

`/volume.html` 同样读取 SQLite，按“交易对优先、账户其次”排序，仅展示近 10 个 UTC 自然日内有真实成交的账户/交易对组合。

### 15.4 统计口径

- 总成交量 = 买入成交额 + 卖出成交额；
- 手续费优先使用交易所实际 commission，并换算为 USDT；
- 已实现净盈亏只计算已经卖出的数量，不包含仍持有仓位的浮动盈亏；
- 如果手续费资产暂时无法换算，页面会标记换算不完整，而不是静默当作完整结果；
- WebSocket 与 REST 对账可能重复看到同一成交，`processed_trade` 表按账户、交易对和成交身份去重，避免重复记账。
- `trade_fill` 按每笔成交保存价格、数量、成交额、手续费和时间；统计依据成交而不是委托订单，一个订单出现多次部分成交时会有多行。
